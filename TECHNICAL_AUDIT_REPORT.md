## 1. Анализ кода и механики воркеров (Celery + Redis)

### 1.1 Общая схема пайплайна

Пайплайн дубляжа состоит из **6 последовательных этапов**:

```
DOWNLOAD → TRANSCRIBE → SAFETY_CHECK → GENDER → TRANSLATE → SPEECH_OPT → TTS → MERGE → [QA] → [S3 Upload] → COMPLETED
```

Каждый этап — это проверка checkpoint'а (сохранены ли промежуточные данные в DB). Если да — этап пропускается. Это ключевой механизм fault-tolerance: при падении worker'а задача не начинается сначала, а продолжает с того места, где остановилась.

### 1.2 Конфигурация Celery

**Файл:** `backend/workers/celery_app.py`

| Параметр | Значение | Назначение |
|----------|----------|------------|
| `worker_prefetch_multiplier` | **1** | Воркер забирает **ровно 1 задачу** за раз из очереди |
| `task_acks_late` | **True** | Подтверждение получения — только после завершения задачи (не при взятии) |
| `task_reject_on_worker_lost` | **True** | Если worker погибает (OOM/SIGKILL), задача автоматически возвращается в очередь |
| `worker_max_tasks_per_child` | **100** | Worker перезапускается каждые 100 задач (защита от memory leaks) |
| `task_time_limit` | **8000 сек** (~2.2 часа) | Жёсткий лимит — worker принудительно убивается |
| `task_soft_time_limit` | **7800 сек** (~2.17 часа) | Мягкий лимит — выбрасывает `SoftTimeLimitExceeded` для graceful shutdown |
| `rate_limit` (process_video) | **1/минуту** | Максимум 1 скачивание YouTube в минуту на worker |

**Очереди:**
- `video_processing_priority` — для Pro/Premium пользователей
- `video_processing` — для обычных пользователей

### 1.3 Механика работы воркера при 5–10 одновременных видео

При текущей конфигурации (`-c 4` = 4并发 воркера в одном контейнере):

#### Что происходит при отправке 5 видео одновременно:

1. **Одновременно в обработке: max 4 задачи** (по числу concurrency)
2. **1 задача стоит в очереди** (Redis), ждёт освобождения слота
3. **Rate Limiter (Redis):** `YoutubeRateLimiter` — строго **1 скачивание YouTube одновременно** (`MAX_CONCURRENT = 1`) с обязательной паузой **30 секунд** между скачиваниями (`MIN_COOLDOWN = 30`)

#### Хронология при 5 видео:

```
t=0:00   — Видео 1: DOWNLOAD (скачивание ~2-5 мин, зависит от размера)
t=0:30   — Видео 1: скачивание завершено, rate limiter разблокирован
t=0:30   — Видео 2: DOWNLOAD начинается (если concurrency позволяет)
...
t=0:30-2:30 — Видео 1: TRANSCRIBE (OpenAI Whisper API, ~1-3 мин для 10 мин видео)
t=0:30-2:30 — Видео 1: TRANSLATE (GPT-4o, ~30 сек на чанк)
t=3:00-5:00 — Видео 1: TTS (Edge TTS / ElevenLabs, ~1-2 мин)
t=5:00-7:00 — Видео 1: MERGE (FFmpeg, ~2-5 мин)
```

**Итого на одно 10-минутное видео: ~10–20 минут** в зависимости от нагрузки на API.

#### При 10 видео:
- 4 в обработке, 6 в очереди Redis
- Rate limiter создаёт "очередь из очередей" — даже если 4 worker'а свободны, скачивание идёт по одному
- **Узкое место №1: YouTube Rate Limiter** — 30-секундная пауза между скачиваниями
- **Узкое место №2: FFmpeg CPU** — merge-intensive этапы нагружают CPU

### 1.4 Redis-блокировки и rate limiter

**Два уровня защиты:**

1. **Redis NX-лок дублей** (`job:running:{id}`, TTL = 3600 сек):
   - Гарантирует, что каждый job выполняется **ровно 1 раз**
   - Если дубликат приходит (Celery retry, ручная отправка) — молча пропускается
   - При crash worker'а — lock истекает через час и задача может быть переобработана

2. **YouTube Rate Limiter** (`yt_dl:concurrent`, `yt_dl:last_start`):
   - `MAX_CONCURRENT = 1` — строго одно скачивание
   - `MIN_COOLDOWN = 30` — пауза 30 сек между скачиваниями
   - `ACQUIRE_TIMEOUT = 600` — максимум 10 минут ожидания слота
   - `mark_failure()` — экспоненциальный backoff при ошибках (до 5 минут)
   - При "slot not available" — Celery retry с `countdown=120`

### 1.5 Узкие места (bottlenecks)

| Этап | Ресурс | Узкое место |
|------|--------|-------------|
| **DOWNLOAD** | Network + Disk I/O | Rate limiter (1 видео/30 сек), прокси-серверы |
| **TRANSCRIBE** | API (OpenAI) | Rate limits Whisper API, квота OpenAI |
| **TRANSLATE** | API (GPT-4o) | Rate limits, квота OpenAI |
| **TTS** | API + Disk I/O | ElevenLabs concurrency limits (5 потоков), Edge TTS — CPU |
| **MERGE** | **CPU** | FFmpeg — тяжёлый CPU-bound процесс (video re-encode + audio mix) |
| **Gender Detection** | API (GPT) | Один дополнительный LLM-вызов |

**Критические цифры:**
- **CPU bottleneck:** FFmpeg merge для 30-минутного видео — ~2-5 минут на 4 ядрах
- **RAM:** FFmpeg audio mixing может потреблять 2-4 GB RAM для длинных видео
- **Disk:** Каждый job оставляет на диске: оригинальное видео (~200MB–2GB) + WAV аудио (~100MB) + TTS сегменты + финальное видео. Очистка происходит только после успешного завершения

### 2.1 Текущая конфигурация (без GPU)

Весь пайплайн работает на **CPU**:
- Транскрипция — **OpenAI Whisper API** (облачный, не требует GPU на сервере)

## 3. Оптимальная архитектура продакшена

### 3.1 Предлагаемая схема разделения

```
┌─────────────────────────────────────────────────────────┐
│                    СЕРВЕР 1: API (CPU)                    │
│                  AWS t3.large / Hetzner CX32             │
│                                                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌─────────┐ │
│  │ FastAPI  │  │  Redis   │  │ Postgres │  │  Nginx  │ │
│  │ Backend  │  │ Broker   │  │ Database │  │ + HTTPS │ │
│  └──────────┘  └──────────┘  └──────────┘  └─────────┘ │
│                                                          │
│  • 4 worker processes (uvicorn)                         │
│  • 12 GB RAM, 4 vCPU                                   │
│  • НЕ обрабатывает видео — только API + Web            │
└─────────────────────────────────────────────────────────┘
                           │
                    Redis Queue
                    (video_processing)
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│              СЕРВЕР 2: GPU Worker                        │
│          RunPod A5000 / Vast.ai T4 / AWS g4dn.xlarge    │
│                                                          │
│  ┌──────────────────┐  ┌─────────────────────────────┐  │
│  │  Celery Worker   │  │  FFmpeg + CUDA              │  │
│  │  -c 2 (GPU)     │  │  (hw accelerated decode)    │  │
│  └──────────────────┘  └─────────────────────────────┘  │
│                                                          │
│  • Подключается к Redis на Сервере 1 (VPN/Direct)       │
│  • 8-16 GB RAM, 4+ vCPU, GPU T4/A5000                  │
│  • ОБРАБАТЫВАЕТ все тяжёлые задачи                      │
│  • Сам масштабируется: можно запустить 2-3 воркера     │
└─────────────────────────────────────────────────────────┘
```

### 3.2 Ключевые преимущества разделения

| Проблема сейчас | Решение |
|-----------------|---------|
| API падает при нагрузке на FFmpeg | API на отдельном сервере, никогда не нагружается GPU-задачами |
| OOM kill worker'ов при параллельных merge | GPU-сервер с достаточным RAM (16+ GB) только для обработки |
| SQLite/Postgres под нагрузкой | Postgres на CPU-сервере, изолирован от обработки видео |
| Нет возможности масштабировать обработку | Добавление GPU-воркеров = просто +1 сервер в Celery cluster |

### 3.3 Масштабирование воркеров

**Текущая проблема:** один контейнер `worker` с `-c 4` — не масштабируется без Docker Compose.

**Решение — Horizontal scaling:**

```bash
# Запуск 3 GPU-воркеров на разных серверах:
# Сервер 1 (API): redis, postgres, backend
# Сервер 2 (GPU-1): celery worker -c 2
# Сервер 3 (GPU-2): celery worker -c 2

# Redis — внешний (на API-сервере), доступен по VPN/IP
CELERY_BROKER_URL=redis://:password@API_SERVER_IP:6379/0
```

**Ключевые правила масштабирования:**
1. **Redis всегда на API-сервере** — он lightweight, не требует GPU
2. **Каждый GPU-воркер** подключается к одному и тому же Redis
3. **Concurrency = 2 на GPU-воркере** — FFmpeg + TTS не должны конкурировать за GPU память
4. **Rate limiter (Redis)** автоматически ограничивает скачивания — добавление воркеров не ломает YouTube rate limits

### 3.4 Защита базы данных

- **PostgreSQL** остаётся на API-сервере — GPU-воркеры подключаются к нему через TCP
- SQLAlchemy `SessionLocal()` — каждый вызов создаёт новую сессию, old sessions закрываются
- `_mark_job_failed()` — использует **отдельную сессию** для обновления статуса (защита от crash)
- **Max connections:** Postgres по умолчанию 100 — при 2-3 GPU-воркерах (4-6 workers) + 4 API workers = ~10-15 соединений, запас огромный

### Технический отчёт по системе дубляжа GapirAI.uz

**Лочинбек, привет!**

Провели полный аудит технической части GapirAI.uz. Вот что нашли и что предлагаем.

#### Как сейчас работает обработка видео

Когда вы отправляете видео на дубляж, система проходит **6 этапов**:

1. **Скачивание с YouTube** (~2–5 минут) — видео скачивается через специальную программу с защитой от блокировок YouTube
2. **Превращение речи в текст** (~1–3 минуты) — Whisper (модель OpenAI) слушает видео и записывает, что говорит ведущий
3. **Проверка контента** (мгновенно) — автоматическая проверка на запрещённый контент
4. **Определение пола ведущего** (~5 секунд) — чтобы подобрать мужской или женский голос
5. **Перевод на узбекский** (~30 секунд) — GPT-4 делает профессиональный перевод
6. **Создание голоса** (~1–2 минуты) — TTS-система создаёт узбекский озвученный трек
7. **Склейка видео** (~2–5 минут) — FFmpeg объединяет оригинал и узбекский голос

**Итого: одно 10-минутное видео обрабатывается ~10–20 минут.**

#### Почему это занимает время

Главная причина — **все вычисления идут на обычном процессоре (CPU)**, без видеокарты. Это как если бы вы рендерили видео на офисном компьютере вместо специального сервера.

Конкретно:
- **FFmpeg** (склейка видео) — очень нагружает процессор
- **Одновременно обрабатывается только 1 видео** для скачивания с YouTube (защита от блокировок)
- При большом количестве видео — они стоят в очереди и ждут

#### Какие серверы нужны для быстрой работы

Мы рассчитали стоимость GPU-серверов (с видеокартой) для ускорения:

| Вариант | Что получаете | Стоимость в месяц |
|---------|--------------|-------------------|
| **AWS g4dn.xlarge** (рекомендуем) | NVIDIA T4, 4 ядра, 16 ГБ RAM | ~$379 (~34,000 сум) |
| **RunPod A5000** (бюджетный) | RTX A5000, 4 ядра, 16 ГБ RAM | ~$194 (~17,500 сум) |
| **Vast.ai T4** (самый дешёвый) | NVIDIA T4, 4 ядра, 16 ГБ RAM | ~$87–173 (~8,000–15,600 сум) |

**С видеокартой обработка ускорится в 3–5 раз** — вместо 10–20 минут, видео будет готово за 3–5 минут.

#### Пошаговый план внедрения GPU

**Этап 1 (1 неделя): Подготовка**
- Разделяем систему на 2 части: "лёгкий" сервер (API + база данных) и "тяжёлый" сервер (GPU + обработка видео)
- Настраиваем безопасное соединение между серверами

**Этап 2 (3–5 дней): Установка GPU-воркера**
- Разворачиваем GPU-сервер с видеокартой
- Переключаем обработку видео на новый сервер
- Тестируем на 5–10 видео параллельно

**Этап 3 (2–3 дня): Оптимизация**
- Настраиваем параллельную обработку (2–4 видео одновременно)
- Добавляем автоматическое масштабирование (при нагрузке подключаются дополнительные GPU)
- Финальное тестирование

**Итого: ~2 недели от начала до продакшена.**

#### Рекомендация

Для старта建议使用 **RunPod A5000 ($194/мес)** — оптимальное соотношение цены и производительности. При росте нагрузки можно легко переключиться на AWS или добавить второй GPU-сервер.
